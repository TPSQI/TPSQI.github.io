一个人也值得好好提交：我的 Git 工作流

木质脚手架发布于 2025 年 8 月 30 日阅读约 2 分钟

有人问我：就你一个人写，Git 不是 add . 然后 commit -m "update" 就行了吗？

三个月前的我确实这样。直到某天要回滚一个两周前的改动，对着一堆「update」「fix」「tmp」提交记录，读出了悬疑小说的感觉。

为什么独狼也要认真提交

Git 提交记录本质上是写给未来自己的文档。它的读者场景非常具体：

  • 半年后排查「这个行为是哪次改的」；
  • 想撤销某个功能，但不想连带撤掉无关修复；
  • 给项目写 CHANGELOG 时的原始素材。

不写清楚，未来的你会用同样的成本骂现在的你。

我的分支模型：能少则少

复杂模型（Git Flow、trunk-based）是为多人协作的沟通成本服务的。一个人写，沟通成本为零，所以分支也应趋向零：

main          ← 随时可发布，只接受能跑的代码
└─ feat/xxx   ← 生命周期通常不超过一天

规则只有三条：

  1. 改动超过一天还没完成 → 开分支；
  2. 当天能收尾的小改动 → 直接在 main 上分批提交；
  3. 永远不要让 main 处于「跑不起来」的状态。

提交信息的三段式

我用一个极简模板：

<类型>: <一句话说明>

为什么改（可选）：
- 补充背景、关联的 issue、权衡的取舍

类型我只记五个，够用了：

类型含义
feat新功能
fix修 bug
docs只改文档
style不改逻辑的格式调整
refactor重构，行为不变

例：

fix: 修复移动端下目录遮挡正文的问题

TOC 在窄屏改为折叠面板后没有重置高度，
滚动到二级标题时会盖住文章。改为显示时重新计算 max-height。

三个月下来，git log --oneline 已经变成我能直接「阅读」的项目编年史。

提交粒度：一次只做一件事

这是最难也最值钱的习惯。判断标准很实用：

这个提交的 diff，能用一句话讲清楚吗？

如果回复里出现「还有」「顺便」「以及」，就该拆成两个提交。

好处在回滚时会加倍奉还：git revert 精准打击，不必在一团毛线里抽丝。

打标签：给里程碑留门

每完成一个可用的版本，我会打一个带说明的标签：

git tag -a v0.3.0 -m "支持导出 Markdown 与本地搜索"

一年后 git tag -l 列出来，就是这个项目的骨架X光片——哪根杆件什么时候立起来的，一目了然。

小结

工具的讲究程度，反映的是你与未来自己的关系。

一个人写代码已经够孤独了，别让提交记录也变成乱码。好好提交，是独行者给自己的路标。
