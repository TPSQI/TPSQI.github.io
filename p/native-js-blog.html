从零用原生 JavaScript 搭一个属于自己的博客

木质脚手架发布于 2026 年 9 月 10 日阅读约 4 分钟

每年都有人问：2026 年了，为什么还要用原生 JS 写博客？

我的答案很简单：因为博客最不该做的事，就是被工具链绑架。

我们要一个什么样的博客

开工之前先写三条验收标准：

  1. 纯静态文件，扔到任意静态托管（GitHub Pages、Nginx……）就能公开访问；
  2. 换一台电脑，拷贝文件夹就能继续写，不依赖本地服务；
  3. 功能完整：列表、详情、分类、标签、归档、搜索，一样不少。

当目标被写得足够具体，技术选型就自动收敛了——静态文件 + 原生 JS。

数据层：一个全局对象就是数据库

所有文章集中放在 js/articles.js 里：

window.BLOG = {
  title: '木质脚手架',
  author: '木质脚手架',
  posts: [
    {
      slug: 'hello-world',
      title: '第一篇文章',
      date: '2026-01-01',
      category: '技术',
      tags: ['前端'],
      excerpt: '摘要会出现在列表页……',
      content: `# 正文是 Markdown`
    }
  ]
};

为什么不用 JSON 文件？因为数据用 <script> 注入全局对象，既能被构建脚本读取来预渲染，也避免了额外的请求时序问题——一个文件就是完整数据层。

渲染层：一个 200 行的 Markdown 解析器

博客正文用 Markdown 写，浏览器却不认识 Markdown，所以需要一个小解析器。核心思路是按行扫描 + 状态切换：

  • 遇到 ` → 进入代码块状态，原样收集到结束；
  • 遇到 # → 输出标题，并顺手记进目录数据；
  • 遇到 > → 收集引用段，递归渲染；
  • 遇到空行 → 结束当前段落。

行内格式（加粗、链接、行内代码）用正则处理，但要先抠出代码片段做占位，否则代码里的星号会被误伤成加粗。

function inline(text) {
  const codes = [];
  text = text.replace(/`([^`]+)`/g, (_, c) => {
    codes.push(c);
    return '\u0000' + (codes.length - 1) + '\u0000';
  });
  // ……处理加粗、链接……
  return text.replace(/\u0000(\d+)\u0000/g, (_, i) =>
    '<code>' + escapeHtml(codes[+i]) + '</code>');
}

不追求支持 CommonMark 全集，只支持我写作时真正会用到的语法——这是个人项目最重要的自由。

视图层：按页面分发的小型路由

每个 HTML 页面只负责自己的结构，共享逻辑放在 app.js：

const page = document.body.dataset.page;
switch (page) {
  case 'home':    renderHome(); break;
  case 'post':    renderPost(); break;
  case 'archive': renderArchive(); break;
  // ……
}

文章页会被构建脚本预渲染成独立文件（p/why-wooden-scaffold.html），正文中读者不依赖 JavaScript 也能打开；客户端脚本再在其上增强目录高亮、搜索与留言。链接统一由 postUrl() 生成，改一处即可全站生效。

那些「顺手」加上功能

骨架立起来之后，才是加横杆的时机：

功能实现要点
暗色模式data-theme 挂在 html 上，localStorage 记忆
全文搜索把标题、摘要、正文拼成字符串，indexOf 模糊匹配
本地留言评论按 slug 存进 localStorage
阅读进度scroll 事件换算百分比，写给顶部进度条
文章目录解析 Markdown 时收集标题，IntersectionObserver 高亮

每一项都不超过 50 行代码，但每一项都真实提升了阅读体验。

完成之后

最终这个博客没有 package.json，没有 node_modules，整个站点就是一个文件夹。

它当然有缺点：没有 SSR、没有评论后台、搜索是暴力遍历。但对一个个人博客来说，能跑、好改、带得走，比什么都重要。

脚手架搭好了，接下来该往上面挂文章了。
